# Architecture

Survive on Earth is a small, dependency-light Babylon.js application. `Game` owns the lifetime of cohesive systems but does not contain their implementation.

- `config/`: centralized defaults and persisted calibration data.
- `input/`: keyboard and pointer joystick, combined as one normalized screen-space vector.
- `interaction/`: explicit interactable contracts, deterministic proximity selection with hysteresis, and contextual action execution/feedback.
- `harvesting/`: deterministic resource hit state, tap/hold swing sessions, live PlayerInventory-backed tool availability, and the runtime bridge from the existing contextual target to player/resource feedback.
- `items/`: Babylon/DOM-free item definitions, read-only registry, immutable validated stacks, split/merge operations, and resource-result contracts.
- `ground-loot/`: runtime ItemStack world entities, deterministic materialization/placement, procedural presentation, and one-shot pickup transactions.
- `inventory/`: pure 10-slot player storage, deterministic capacity planning, atomic stack insertion, and read-only snapshots.
- `equipment/`: pure four-slot armor state, guarded Inventory transfer coordinator, deterministic calibration fixtures, a thin player-visual projection, and a separate single-slot active Weapon domain (`PlayerWeaponSlot` + `WeaponEquipSystem`) that never touches armor totals.
- `crafting/`: pure starter recipe definitions, immutable recipe registry, inventory-derived craftability, and the thin atomic crafting coordinator.
- `combat/`: pure health/target contracts, explicit deterministic target registration and selection, timed melee attack state machine with profile resolution from Weapon Slot / unarmed fallback, pure LDOE-style Player armor mitigation, Player incoming-damage resolution against live equipment, and a thin Babylon/DOM presentation adapter.
- `enemies/`: centralized Roaming Zombie calibration, a pure CombatTarget-backed AI state machine, a narrow multi-agent coordinator that delivers raw attack damage only, and procedural Babylon presentation.
- `player/`: procedural visual, animation, movement state, collision-aware controller, and held-weapon + harvest tool visuals.
- `camera/`: fixed orthographic camera with exponential smoothing.
- `collision/`: deterministic 2D circle/AABB collision and sliding; rendering meshes are never collision geometry.
- `world/`: deterministic procedural test location and mathematical building grid.
- `rendering/`: generated textures, shared stylized materials, daylight/shadows, quality presets, and restrained image processing.
- `world/detail/`: procedural ground surface and preset-scaled thin-instance clutter with no gameplay presence.
- `debug/`: live calibration controls and non-gameplay diagnostics.
- `debug/FidelityMode`: local-only F3 reference upload, comparison views, guides, and presentation freeze; reference images are never persisted.
- `ui/`: responsive LDOE-aligned HUD, presentation-only minimap, resource-result feedback, and one modal loadout view bound to Inventory, Equipment, and Weapon Slot snapshots.
- `config/hudLayoutConfig`: centralized normalized HUD anchors/sizes and lightweight validation.

The update order is input → combat target selection/attack request → player movement gating/collision → player melee timing/impact → enemy AI movement/attack/impact → interaction selection → harvesting/contextual action → combat/world presentation → HUD/minimap → camera → Ground Loot presentation → debug. Resolving player melee before enemy AI guarantees that a Zombie killed in the current frame cannot produce a later phantom impact. Physical keyboard/pointer input becomes semantic movement plus separate primary-action and attack press states before gameplay systems consume it. Inventory, Crafting, or Fidelity-panel visibility suppresses Player input and cancels an active harvest without pausing world/render updates; hostile AI therefore remains dangerous behind gameplay panels. F3 motion freeze passes zero delta to both combat paths. Non-resource interaction, pickup, and attack use discrete press edges; only harvesting consumes hold cadence. All time-based systems use a clamped delta time.

`World` exposes one explicit collection of `Interactable` descriptors. Harvestable resources and active Ground Loot implement that same contract, so the interaction layer remains the only target selector and never scans the Babylon scene graph. A harvest session temporarily locks its selected descriptor without replacing selector hysteresis. Resource hit state and yield data are deterministic; tree/rock visuals only receive impact/depletion callbacks. On the accepted final impact, the item domain builds one immutable `ItemResult` and passes it through a composite `ResourceResultSink` to floating feedback plus **direct Inventory delivery** (`HarvestRewardDelivery`) — not Ground Loot materialization.

Combat targeting is intentionally parallel to, not merged with, contextual interaction. `CombatTargetSystem` considers only explicitly registered `CombatTarget` instances, selects deterministically by distance and runtime ID, and applies a small switch bias. `MeleeCombatSystem` resolves the Player attack profile from `PlayerWeaponSlot` (or unarmed fists), locks target **and** profile when an attack begins, schedules exactly one impact from that snapshot, and revalidates registration, life state, and hit range at impact. Successful tool impacts spend one shared `ItemStack.currentDurability` point; fists never wear. The attack blocks movement only before impact; recovery permits movement. `HealthPool`, combat targets, and combat timing remain Babylon/DOM-free, while `CombatPresentation` owns dummy meshes, target/health UI, damage numbers, recoil, and death cleanup.

`HealthPool` is also the sole Player-health source. The Player owns a 100-point pool read directly by HUD and F2. Zero health enters a minimal terminal gate that cancels movement, combat, harvesting, and interaction input while rendering continues; it is not a production death/respawn system. Incoming enemy damage is resolved on the Player side only: `PlayerDamageResolver` reads live `PlayerEquipment.totalArmor` at impact time, applies pure LDOE armor mitigation (`DamageReduction = Armor / (Armor + 50/3)` with nearest-whole rounding), then commits the final amount to `HealthPool`. Equip/unequip mid-windup therefore changes the next impact without caching armor inside enemy AI. `RoamingZombie` implements the unchanged `CombatTarget` contract and adds pure IDLE/CHASE/ATTACK/RECOVERY/DEAD behavior alongside it. Thus every current Enemy is a CombatTarget, but passive Combat Dummies remain CombatTargets without AI. `EnemySystem` provides current Player position/alive state, independent agent updates, raw damage delivery through the Player damage adapter, and one-shot enemy cleanup. It does not select combat targets, own armor totals, or apply mitigation formulas itself.

Enemy navigation is intentionally direct XZ steering through the existing deterministic collision solver. Dynamic enemy circles are synchronized after movement and ignored only by their own mover; no physics, pathfinding, navmesh, line-of-sight, or obstacle planning exists. A blocked Zombie may remain stuck. Detection is radial, uses acquire/lose hysteresis, and does not alter contextual interaction.

Visual geometry is allowed to be richer than gameplay geometry. Trees, rocks, the crate, campfire, house fragment, vegetation, and player rendering remain attached to the same stable roots/anchors while collision and interaction data stay unchanged. Procedural textures are generated once and redrawn only during live calibration; environmental clutter uses shared meshes with thin-instance buffers. `World.update` advances only lightweight foliage/fire/smoke presentation.

F3 freeze supplies a zero frame delta and skips player/harvesting/combat simulation for comparison frames. It pauses tool and fist poses, resource reactions, depletion motion, dummy recoil/death motion, pooled impact debris, temporary item-result feedback, and pickup presentation without creating a second state model or mutating gameplay data. The contextual action routes ordinary requests, resource harvesting, or a selected Ground Loot pickup; the dedicated attack action routes only combat requests.

Item dependency flow is harvesting depletion → centralized resource yield (`ItemResult`) → **direct `HarvestRewardDelivery` into `PlayerInventory`** (partial insert, overflow discarded, **no GroundLoot**). Authored world items use a separate flow: `GroundLootSystem.placeAuthoredStack` / historical `materialize` → InteractionSystem → PickupSystem → full-stack-or-nothing `tryInsert`. Equipment calibration armor and M15 starter Pine Log/Limestone fixtures use GroundLoot. The temporary pickup sink is debug observation only.

Equipment transfer flow is Inventory selection → catalog-derived destination slot → guarded whole-stack exchange → PlayerEquipment state → UI and player-visual subscribers. Equipping into an occupied slot returns the old item to the same source Inventory slot, so a swap does not require spare capacity. Unequipping delegates to the existing deterministic Inventory insertion plan; a full Inventory leaves equipment unchanged. PlayerInventory and PlayerEquipment are the only gameplay owners, and their guarded callbacks keep every accepted transfer item-conserving. The Babylon-facing `EquipmentVisualController` is a projection only and never owns equipment truth.

The temporary pickup sink is debug observation only. Inventory UI reads frozen slot snapshots and updates changed slots through local callbacks, never from the Babylon frame loop. The item, Inventory, PlayerEquipment, and EquipmentSystem domains have no Babylon/DOM dependencies.

Crafting dependency flow is immutable `CraftingRecipeRegistry` → `CraftingSystem` inventory-derived state → generic PlayerInventory consume-and-insert simulation → one atomic slot-state commit → Inventory/Crafting UI subscribers. Requirements are counted across all slots and consumed from the lowest index first. Output capacity is evaluated after simulated consumption, so a slot freed by ingredients can receive the crafted item. PlayerInventory knows only generic item requirements and an output stack; it never imports recipe or CraftingSystem concepts. Crafted Hatchet/Pickaxe enter Inventory only (no auto-equip). Harvesting and combat read live tool presence through `HarvestToolResolver` / Weapon Slot. M15 starter GroundLoot Pine Logs and Limestone make bootstrap crafting possible without tools.

Harvesting tool durability (M13/M14) attaches instance `currentDurability` to durable tool `ItemStack`s whose definitions declare `maxDurability` (Hatchet/Pickaxe = 50). Catalog max is read-only metadata; runtime wear never mutates definitions. On each successful harvest impact, `HarvestingSystem` spends exactly one durability through `HarvestToolResolver.consumeImpactUse` (matching equipped Weapon Slot first, else lowest Inventory slot), then applies the resource hit. On depletion, yield is delivered by `HarvestRewardDelivery` (not GroundLoot). Cancelled/rejected swings and wrong/missing tools spend nothing. Inventory UI reuses a production ratio durability bar for inventory and weapon slots; F2 reports weapon combat profile, harvest tool source, and last harvest delivery.

No physics engine, event bus, framework, or global manager is used in Milestone 01.
